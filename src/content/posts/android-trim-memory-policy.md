구글이 2027년 2월부터 시행하는 앱 품질 기준 공지를 봤습니다. 여러 항목 중 메모리 쪽에 이런 문장이 있었습니다.

> 비트맵은 앱이 포그라운드에 있을 때는 메모리를 차지해도 되지만, 백그라운드나 캐시된 상태처럼 화면에 안 보이는 상태에서 오래 들고 있으면 안 된다.

읽고 나서 궁금해졌습니다. 우리 앱은 백그라운드로 넘어가면 실제로 메모리를 놓아줄까. 확인해보니 놓아주지 않고 있었습니다.

## 이 정책이 재는 것

기준은 크게 세 가지인데, 그중 메모리와 직접 관련된 두 개만 짚습니다.

**동적 메모리**는 "Anonymous RSS + Swap"을 봅니다. 말이 어렵게 들리는데 풀어보면 이렇습니다. 앱이 실제로 물리 메모리에 올려둔 데이터 중, 파일에서 그대로 매핑한 게 아니라 앱이 직접 만들어낸 데이터(객체, 캐시, 버퍼)의 크기가 Anonymous입니다. 시스템이 메모리가 부족해지면 이 중 일부를 압축해서 스왑 영역으로 밀어내는데, 밀려났다고 해서 안 쓴 걸로 치지 않습니다. 정책은 이 둘을 더한 값을 봅니다.

**비트맵 메모리**는 별도로 봅니다. 이미지 하나가 화면 크기만큼의 픽셀 데이터를 메모리에 올려두는데, 여러 장을 스크롤하며 봤다면 그만큼 쌓입니다. 포그라운드에 있는 동안은 괜찮지만 화면을 벗어나 **백그라운드나 캐시 상태로 들어간 뒤에도 계속 들고 있으면 걸립니다.
**
## 실기기로 재봤습니다

말로만 보고 넘어가긴 찝찝해서 adb로 직접 확인했습니다. 쓴 명령은 두 개입니다.

```bash
adb shell dumpsys meminfo <패키지명>
adb shell run-as <패키지명> cat /proc/<pid>/smaps_rollup
```

앞의 것은 Java 힙, 네이티브 힙, 그래픽스(비트맵)를 항목별로 나눠 보여주고 뒤의 것은 정책이 실제로 보는 Anonymous와 Swap 값을 그대로 읽어옵니다.

이미지가 많은 화면을 한 바퀴 돌고 홈 버튼으로 백그라운드에 보낸 뒤 값을 재보니, 그래픽스(비트맵) 항목이 시간이 지나도 거의 그대로였습니다. 시스템에 강제로 메모리 회수 신호를 보내는 명령도 있어서 그것도 써봤습니다.

```bash
adb shell am send-trim-memory <pid> COMPLETE
```

시스템이 낼 수 있는 가장 강한 신호를 보낸 건데도 비트맵 메모리가 거의 안 줄었습니다. 원인은 코드를 열어보니 바로 나왔습니다. 이 신호를 받는 콜백 자체를 앱에 구현한 적이 없었습니다.

## onTrimMemory가 뭘 하는 콜백인가

안드로이드는 메모리가 부족해지면 실행 중인 모든 앱에 "지금 상황이 이 정도니 알아서 좀 줄여라"는 신호를 보냅니다. 이 신호를 받는 자리가 `Application` 클래스의 `onTrimMemory(level)`입니다. `level`은 지금 상황이 얼마나 급한지를 나타내는데, 앱이 포그라운드에 있을 때 오는 약한 신호부터 앱이 완전히 화면 밖으로 나갔을 때 오는 신호까지 단계가 나뉘어 있습니다.

이 콜백이 왜 필요하냐면, 안드로이드는 메모리가 부족해지면 백그라운드 프로세스를 순서대로 강제 종료해서 공간을 만드는데, 신호에 반응해서 미리 캐시를 비워두면 종료 대상 순위에서 밀려날 수 있습니다. 반대로 아무 반응이 없으면 시스템 입장에서는 "이 앱은 메모리를 계속 붙잡고 있으니 먼저 정리하자"는 후보가 됩니다.

`onLowMemory()`라는 비슷한 콜백도 있는데, 이건 전체 시스템이 정말 위험한 수준일 때만 한 번 오는 신호라 단계가 없습니다. `onTrimMemory`가 훨씬 촘촘하게 상황을 알려줍니다.

## 왜 아무 반응이 없었나

찾아보니 우리 앱은 이미지 로딩 라이브러리(Glide) 자체 캐시 말고도, 테마 색상을 미리 그려둔 비트맵을 담아두는 캐시와 애니메이션 이미지를 담아두는 캐시를 직접 만들어 쓰고 있었습니다. 둘 다 화면 전환이 잦을 때 이미지가 깜빡이지 않게 하려고 넣은 건데, 정작 언제 비울지에 대한 규칙이 없었습니다. 앱이 켜져 있는 동안 계속 쌓이기만 하는 구조였습니다.

## 고친 방법

`Application` 클래스에 `onTrimMemory`와 `onLowMemory`를 구현하고 캐시들을 한 번에 정리하는 함수 하나로 묶었습니다.

```kotlin
override fun onTrimMemory(level: Int) {
    super.onTrimMemory(level)
    if (level >= TRIM_MEMORY_UI_HIDDEN) clearMemoryCaches()
}

override fun onLowMemory() {
    super.onLowMemory()
    clearMemoryCaches()
}

fun clearMemoryCaches() {
    imageLoader.clearMemory()
    themeColorBitmapCache.clear()
    animatedImageCache.evictAll()
}
```

`TRIM_MEMORY_UI_HIDDEN` 이상에서만 반응하도록 기준을 잡았습니다. 그보다 약한 신호는 앱이 아직 포그라운드에 있는데 시스템 전체 메모리가 빠듯해졌다는 뜻이라, 여기서 캐시를 비우면 화면을 넘길 때마다 이미지가 다시 깜빡이는 대가를 치르게 됩니다. 화면이 완전히 안 보이게 된 시점부터 비우는 게 맞다고 판단했습니다. 백그라운드로 넘어가는 순간에도 같은 함수를 한 번 더 불러서 시스템 신호를 기다리지 않고 먼저 정리합니다.

## 결과와 남은 문제

다시 강제로 회수 신호를 보내보니 이번엔 비트맵 메모리가 확실히 줄었습니다. 시스템이 신호를 보내면 실제로 반응하는 앱이 된 겁니다.

다만 정직하게 적으면, 정책이 재는 "Anonymous + Swap" 총량은 이번 수정만으로 크게 줄지 않았습니다. `dumpsys meminfo`가 비트맵이나 자바 힙으로 잡아주지 않는, 네이티브 쪽에 따로 잡혀 있는 메모리가 상당히 남아 있었습니다. 이건 이미지 캐시 정리로 해결되는 영역이 아니라 별도로 들여다봐야 하는 문제라, 이번엔 건드리지 않고 남겨뒀습니다.

## 정리

- 정책이 보는 동적 메모리는 Anonymous RSS와 Swap을 더한 값이라, 시스템이 압축해서 스왑으로 밀어낸 메모리도 여전히 카운트됩니다.
- 비트맵은 포그라운드에서만 허용되고 백그라운드·캐시 상태에서 계속 들고 있으면 안 됩니다.
- `onTrimMemory(level)`는 안드로이드가 메모리 압박 정도를 단계별로 알려주는 콜백이고 `onLowMemory()`보다 훨씬 세밀합니다.
- 직접 만든 캐시는 이 콜백에 연결해두지 않으면 아무리 잘 설계해도 계속 쌓이기만 합니다.
- adb의 `dumpsys meminfo`와 `smaps_rollup`, 그리고 `am send-trim-memory`로 강제 신호를 보내보는 것만으로도 지금 앱이 실제로 반응하는지 눈으로 확인할 수 있었습니다.
