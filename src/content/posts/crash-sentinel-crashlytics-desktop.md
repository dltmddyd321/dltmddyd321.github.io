회사에서 크래시를 확인하는 방식은 오랫동안 메일이었습니다. Crashlytics가 "발생 빈도가 높아진 안정성 문제"라는 제목으로 메일을 보내면 링크를 눌러 콘솔을 열고, 스택 트레이스를 읽고, 프로젝트에서 해당 코드를 찾아 들어갔습니다. 한두 번이면 괜찮은데 매일 반복하니 이 흐름 자체가 일이 됐습니다.

마침 팀에 AI를 업무에 붙여 보는 시도(AX)를 하고 있었고 그 첫 단계로 이 흐름을 줄여 보기로 했습니다. Claude Code와 대화하면서 macOS용 데스크톱 앱을 하나 만들었고 이름은 Crash Sentinel로 붙였습니다.

![Crash Sentinel 대시보드](/uploads/1793343600000-crash-sentinel-dashboard.png)

> 이슈 이름과 앱 버전처럼 회사 코드가 드러나는 부분은 모자이크 처리했습니다.

## 처음에 원한 것

처음 Claude에게 건넨 요구사항은 네 가지였습니다.

1. 빈도가 높아진 이슈를 알려 주고, 누르면 펼쳐지면서 연결된 프로젝트 코드를 Claude가 빠르게 훑어 요약해 줄 것. 자세한 분석은 토큰과 시간이 아까우니 짧게
2. 최근 48시간 비정상 종료 추이를 타임라인 그래프로 보여 주고, 가장 많이 터진 이슈 Top 3를 옆에 둘 것
3. 화면의 모든 이슈는 누르면 해당 Firebase 이슈 페이지가 열릴 것
4. 가장 최근에 배포한 버전만 따로 볼 수 있는 탭을 둘 것

## 만들다가 방향을 한 번 틀었습니다

첫 버전을 띄워 보고 솔직한 감상은 "이게 Firebase 콘솔을 직접 보는 것보다 나은가?"였습니다. 그래프와 목록은 콘솔에도 있습니다. 같은 정보를 다른 창에서 보는 정도라면 굳이 앱을 하나 더 띄울 이유가 없습니다.

그래서 중심을 분석으로 옮겼습니다. 이슈마다 `ANALYZE` 버튼을 두고 누르면 그 이슈의 스택을 들고 우리 프로젝트 코드에서 원인을 짚어 주는 것이 이 앱만 할 수 있는 일이라고 봤습니다. 대시보드는 어떤 이슈를 분석할지 고르는 화면으로 역할을 낮췄습니다.

## 기술 선택

Mac에서 쓸 앱이라고 했는데 Kotlin 프로젝트가 만들어져서 처음엔 의아했습니다. 물어보니 Compose Desktop이었습니다. 저는 평소 Android를 Kotlin과 Compose로 만들기 때문에 나중에 혼자 고치고 기능을 붙이기에는 Swift보다 이쪽이 낫다는 판단이었고 그대로 가기로 했습니다.

데이터는 Crashlytics `v1alpha` API로 가져옵니다. 인증은 따로 키를 만들지 않고 `gcloud`로 로그인한 계정의 토큰을 씁니다. 앱 설정은 `~/.crashlytics-monitor/config.json` 한 파일에 두고 저장소에는 예시 파일만 올렸습니다.

## 기능

### 크래시 타임라인

최근 48시간을 시간 단위 막대로 보여 줍니다. 막대 색은 그 시간대 건수에 따라 LOW부터 CRIT까지 다섯 단계로 바뀌고 막대에 마우스를 올리면 그 시간대에 많이 터진 이슈와 비중이 나옵니다. 축에는 실제 측정 시각을 찍어 두어서 "어제 오후 몇 시부터 늘었다"를 바로 읽을 수 있습니다.

### Threat Rank, Issue Registry

오른쪽 Threat Rank에는 48시간 동안 가장 많이 터진 이슈 세 개가 크래시 수, 영향받은 사용자 수와 함께 올라갑니다. 아래 Issue Registry는 전체 이슈 목록이고 제목을 누르면 Chrome에서 해당 Firebase 이슈 페이지가 열립니다. 회사 계정 프로필을 지정해 두어서 매번 로그인 화면이 뜨지 않습니다.

목록에는 `EXTERNAL` 배지가 붙는 이슈도 있습니다. 특정 제조사 기기의 시스템 코드처럼 우리 코드가 아닌 곳에서 시작된 크래시를 Claude가 미리 분류해 둔 것입니다. 손댈 수 없는 이슈를 먼저 걸러 내면 볼 목록이 줄어듭니다.

### ANALYZE

이 앱의 핵심입니다. 버튼을 누르면 앱이 Claude Code CLI를 이렇게 실행합니다.

```bash
claude -p "<이슈 요약과 스택>" \
  --model haiku --max-turns 8 \
  --allowedTools Read Grep Glob \
  --output-format json
```

몇 가지를 일부러 제한했습니다.

- 모델은 haiku, 최대 8턴입니다. 처음 요구사항대로 깊은 분석보다 빠른 1차 진단이 목적이라서입니다
- 도구는 읽기(`Read`, `Grep`, `Glob`)만 허용합니다. 분석 중에 코드가 바뀌면 안 됩니다
- 크래시가 난 버전의 릴리스 태그를 찾아 그 시점 코드를 기준으로 봅니다. 태그가 없으면 가장 가까운 태그로 근사하고, 그렇게 했다고 결과에 적습니다
- 이전 릴리스 태그와 비교해서 그 사이에 들어간 커밋을 "의심 커밋"으로 같이 넘깁니다
- 이벤트 데이터에서 사용자 정보 같은 개인정보 필드는 모델에 보내기 전에 뺍니다

결과는 원인 2~3문장, 위치(파일경로:라인), 수정 방향 1~2문장, 신뢰도(높음·중간·낮음) 네 줄로만 받습니다. 길게 받으면 결국 다시 읽어야 하니까요.

### 급증 알림

10분마다 직전 1시간 건수를 그 전 24시간의 시간당 평균과 비교합니다. 3배를 넘거나, 전에 없던 이슈가 5건 이상 나오면 Mac 알림을 띄웁니다. 같은 이슈로 알림이 계속 울리지 않도록 6시간 동안은 다시 알리지 않습니다. 기준값은 모두 설정 파일에서 바꿀 수 있습니다.

### 그 밖에

- 상단 드롭다운으로 Android와 iOS 앱을 바꿔 봅니다
- `LATEST` 탭은 가장 최근 배포 버전만 따로 보여 줍니다
- 로그인할 때 자동으로 실행되고 메뉴 막대 트레이에 상주합니다

## 쓰면서 고친 것들

만든 날 끝난 앱은 아니었습니다. 매일 쓰면서 걸리는 부분을 Claude에게 그대로 말하고 고쳤습니다.

- **아침마다 다시 로그인**: Mac을 켤 때마다 Google 로그인을 요구했습니다. 자동 실행 환경에서는 `gcloud` 재로그인 창이 뜨지 않는 문제가 겹쳐 있었고 토큰이 만료되면 새로 받아 한 번 더 시도하도록 바꿨습니다
- **탭마다 다른 인증 상태**: 전체 탭에서 로그인해도 최신 버전 탭이 이전 실패 상태를 그대로 보여 줬습니다. 탭을 열 때 상태를 다시 읽게 했습니다
- **알림을 누르면 스크립트 편집기**: 처음에는 `osascript`의 `display notification`으로 알림을 띄웠는데, macOS는 이 알림을 스크립트 편집기 소유로 봅니다. 그래서 알림을 누르면 Crash Sentinel이 아니라 스크립트 편집기가 열렸습니다. 앱 자체 트레이 알림으로 바꾸고 앱이 앞으로 올 때 창을 열도록 했습니다
- **분석할 때마다 작업 폴더 생성**: 릴리스별로 git worktree를 만들어 분석했더니 폴더가 계속 쌓였습니다. 메인 저장소에서 바로 분석하도록 바꿨습니다

## 정리

결국 이 앱이 줄인 건 "메일 → 콘솔 → 스택 → 코드" 사이의 이동입니다. 그래프는 덤이고 실제로 시간을 아껴 주는 건 이슈를 눌렀을 때 우리 코드의 어느 파일, 어느 줄을 먼저 봐야 하는지 짧게 알려 주는 부분입니다. haiku가 내놓는 진단이 늘 맞지는 않습니다. 그래도 어디서부터 볼지 정해 주는 것만으로 첫 10분이 꽤 줄었습니다.

처음 "이게 콘솔보다 나은가"를 물었던 게 이 앱의 방향을 정했다고 생각합니다. 기능을 붙이기 전에 그 질문부터 하는 습관을 남겨 둘 생각입니다.
