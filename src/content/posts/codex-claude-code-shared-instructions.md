Claude Code를 메인으로 쓰다가 특정 작업엔 Codex도 같이 써보기로 했습니다. 그러면서 프로젝트 지시 파일을 어떻게 구성할지 다시 정리할 필요가 생겼습니다. 겪은 과정을 기록해봅니다.

## 벤더마다 다른 이름을 요구한다

Claude Code는 저장소 루트의 CLAUDE.md를 읽고 Codex는 같은 역할을 AGENTS.md라는 파일명으로 읽습니다. 내용은 사실상 같아야 하는데, 파일명은 벤더가 정해둔 대로 따라야 합니다. 하나로 합쳐서 끝낼 수 없는 구조입니다.

## 손으로 동기화하다 브랜치에서 깨졌다

처음엔 단순하게 접근했습니다. 두 파일을 각각 만들어두고 규칙이 바뀔 때마다 양쪽 다 고쳤습니다.

문제는 이게 롱리빙 브랜치가 여러 개로 갈라지는 순간부터였습니다. 한 브랜치에서 "두 파일을 동기화한다"는 관례 자체를 커밋으로 남겨뒀는데, 그보다 먼저 갈라진 다른 브랜치에는 그 커밋이 애초에 존재하지 않았습니다. 그 브랜치에서 작업하는 동안엔 AGENTS.md라는 파일이 있다는 사실조차 알 수 없었던 셈입니다. 규칙을 지키자고 만든 파일이, 정작 규칙이 필요했던 브랜치에는 없었습니다.

```mermaid
gitGraph
    commit id: "공통 조상"
    branch 브랜치-B
    checkout main
    commit id: "이후 작업 계속"
    branch 브랜치-A
    checkout 브랜치-A
    commit id: "AGENTS.md 동기화 관례 추가"
    checkout 브랜치-B
    commit id: "이번 작업"
```

브랜치-B는 그 관례가 생기기 전에 이미 갈라져 나간 상태였습니다. main에서 나중에 파생된 브랜치-A에만 그 커밋이 남았고, 브랜치-B는 main과도, 브랜치-A와도 합쳐진 적이 없어 그 존재 자체를 알 방법이 없었습니다.

같은 문제가 재사용 워크플로 정의(반복 작업을 고정된 절차로 적어둔 스킬 파일들)에서도 나타났습니다. 프로젝트 로컬 디렉토리에 커밋해둔 워크플로 몇 개가 다른 브랜치를 체크아웃하면 그냥 사라졌습니다. 브랜치를 옮길 때마다 있는지 없는지부터 확인하고 없으면 다시 만드는 일을 반복했습니다.

## 브랜치 종속과 무관을 나눈다

돌이켜보면 원인은 하나였습니다. 브랜치마다 달라져도 되는 것과, 브랜치와 무관하게 항상 같아야 하는 것을 구분하지 않고 전부 저장소 커밋에만 의존했다는 점입니다. 저장소 커밋에 의존하는 자원은 그 저장소의 브랜치 그래프를 그대로 따라갑니다. 병합되기 전까지는 존재하지 않는 게 정상 동작이고 그건 버그가 아니라 git이 원래 그렇게 동작하는 것뿐입니다.

그래서 정리 기준을 이렇게 잡았습니다.

| 구분 | 기준 | 둔 위치 |
|---|---|---|
| 재사용 워크플로 | 특정 프로젝트 상태를 가정하지 않고 실행 시점에 스스로 전제조건을 확인한 뒤 분기한다 | 개인 홈 디렉토리 아래 전역 스킬 폴더 |
| 프로젝트 고유 파이프라인 | 그 저장소의 디렉토리 구조·네이밍에 강하게 묶여 있다 | 프로젝트 로컬 |
| 프로젝트 지시 파일 | 스택 정보, 아키텍처, 코딩 컨벤션처럼 그 프로젝트 고유의 내용이다 | 프로젝트 로컬(단, 벤더별 파일 두 개는 유지) |

첫 번째 줄에 해당하는 워크플로는 저장소 히스토리 밖으로 완전히 빼버렸습니다. 개인 전역 디렉토리는 어느 저장소, 어느 브랜치를 열든 항상 로드되기 때문에 브랜치 이력과 아예 무관해집니다. 두 번째 줄처럼 그 저장소에만 의미 있는 것들은 그대로 로컬에 남겨뒀습니다. 다른 프로젝트로 옮겨봤자 쓸 데가 없기 때문입니다.

## 남는 문제는 복제였다

세 번째 줄이 남습니다. 프로젝트 지시 파일 본문은 전역으로 뺄 수 없습니다. 이 프로젝트만의 내용이라 저장소 안에 있어야 맞습니다. 그런데 벤더가 요구하는 파일명이 다르니, 결국 두 개를 만들어야 하고 두 개를 만들면 복제가 생기고 복제가 생기면 한쪽만 고치고 잊어버리는 일이 또 반복됩니다.

Claude Code 문서를 다시 찾아보니 `@경로` 문법으로 다른 파일의 내용을 그대로 불러올 수 있다는 걸 확인했습니다. 이 문법을 코드 블록 바깥에 적어두면, Claude Code가 세션을 시작할 때 그 경로의 파일 내용을 읽어와 그 자리에 그대로 펼쳐 넣습니다.

그래서 복제 대신 참조로 바꿨습니다. AGENTS.md를 원본으로 두고 CLAUDE.md는 다음 한 줄만 남겼습니다.

```
@AGENTS.md
```

Claude Code에만 필요한 지시가 생기면 이 한 줄 아래에 이어서 적으면 됩니다. AGENTS.md 쪽은 계속 원본으로 관리하고 CLAUDE.md는 그 내용을 그대로 물려받습니다. 이제는 규칙을 고칠 때 파일 하나만 건드리면 되고 두 파일이 다시 벌어질 일도 없습니다.

## 느낀 점

벤더가 하나였을 때는 "이 설정을 어디에 둘까"라는 질문 자체가 잘 떠오르지 않았습니다. 파일 하나, 저장소 하나면 충분했으니까요. 벤더가 둘이 되고 나서야 같은 정보를 두 곳에 두어야 하는 상황이 생겼고 그제서야 프로젝트 고유인지 범용인지, 브랜치에 종속돼도 되는지 아닌지를 구분하는 기준이 필요해졌습니다.

돌아보면 이번에 겪은 문제는 새로운 종류가 아니었습니다. 여러 환경에 흩어져 있는 설정을 한 군데에서 관리하고 싶다는 건 인프라 코드에서도, dotfiles에서도 늘 나오는 얘기입니다. 다만 그 대상이 이번엔 사람이 아니라 에이전트가 읽는 파일이었을 뿐입니다.
