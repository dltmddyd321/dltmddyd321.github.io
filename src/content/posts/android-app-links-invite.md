캘린더를 다른 사람과 같이 쓰려면 초대 링크를 보내야 합니다. 지금까지 이 초대 링크는 외부 링크 서비스인 Branch가 만들어 줬습니다. 링크를 만들 때 SDK를 호출하면 짧은 주소가 나오고 받은 사람이 누르면 Branch가 앱을 열어 주면서 초대 키를 넘겨 주는 방식이었습니다.

편하긴 했지만 링크 하나가 외부 서비스를 거쳐야 했습니다. 링크 주소도 우리 도메인이 아니었고 링크가 어떻게 처리되는지도 SDK 안에 숨어 있었습니다. 그래서 초대 링크부터 Branch를 걷어내고 우리 도메인의 https 주소 끝에 초대 키를 붙이는 Android App Link로 바꿨습니다. 작업하면서 딥 링크와 앱 링크가 정확히 어떻게 다른지 다시 정리하게 됐고 서버와 웹 쪽에서 챙길 일도 생각보다 많았습니다. 그 과정을 순서대로 적어 봅니다.

## 딥 링크와 앱 링크는 무엇이 다른가

Android 문서에서 딥 링크는 넓은 말입니다. 링크를 눌렀을 때 앱의 특정 화면으로 바로 들어가게 해 주는 것을 모두 딥 링크라고 부릅니다. 앱 링크는 그중에서 **도메인 소유권 검증까지 통과한 https 링크**를 따로 부르는 이름입니다. 그래서 보통 "딥 링크 vs 앱 링크"라고 할 때의 딥 링크는 `myapp://invite/abc` 같은 커스텀 스킴 링크를 뜻합니다.

![딥 링크와 앱 링크의 동작 비교](/uploads/1792990000000-applink-vs-deeplink.svg)

커스텀 스킴은 등록이 쉽습니다. manifest에 스킴 이름만 적으면 됩니다. 문제는 아무도 그 이름의 주인을 확인하지 않는다는 점입니다. 다른 앱이 같은 스킴을 등록하면 사용자에게 앱 선택 창이 뜨거나, 엉뚱한 앱이 링크를 받아 갈 수 있습니다. 앱이 설치되지 않은 기기에서는 갈 곳이 없어서 아무 일도 일어나지 않거나 브라우저가 오류 페이지를 보여 줍니다. 메신저로 주고받는 링크로는 쓰기 어렵습니다. 대부분의 메신저가 `https`가 아닌 주소는 링크로 인식하지도 않습니다.

앱 링크는 평범한 https 주소입니다. 대신 앱을 설치할 때 OS가 그 도메인에 "이 앱이 정말 이 도메인의 주인이 맞는지" 물어보고 서버가 맞다고 답한 경우에만 링크를 앱으로 보냅니다. 검증을 통과하면 선택 창 없이 바로 앱이 열리고 앱이 없으면 같은 주소의 웹 페이지가 열립니다. 링크 하나로 앱 사용자와 앱이 없는 사용자를 모두 받을 수 있습니다.

| | 딥 링크 (커스텀 스킴) | 앱 링크 |
|---|---|---|
| 주소 형태 | `myapp://...` | `https://도메인/...` |
| 소유권 검증 | 없음 | 서버의 `assetlinks.json`으로 검증 |
| 다른 앱이 가로챌 수 있나 | 있음 | 없음 |
| 앱이 없을 때 | 갈 곳 없음 | 같은 주소의 웹 페이지 |
| 메신저에서 링크로 인식 | 대부분 안 됨 | 됨 |
| 준비할 것 | manifest만 | manifest + 도메인 + 서버 파일 |

참고로 Android 12부터는 검증되지 않은 https 링크를 누르면 앱 선택 창 대신 그냥 브라우저가 열립니다. 예전처럼 "검증은 안 됐어도 선택 창에서 앱을 고르면 되겠지"가 통하지 않습니다. https 주소로 앱을 열고 싶다면 검증이 사실상 필수입니다.

iOS에는 같은 역할을 하는 Universal Link가 있습니다. 개념은 비슷하지만 서버 파일 이름(`apple-app-site-association`)도, 처리 방식도 달라서 따로 준비해야 합니다. Android 쪽에서는 Universal Link라는 말을 쓰지 않고 App Link라고 부릅니다.

## 주소부터 정했습니다

초대 링크 주소는 이렇게 정했습니다. 도메인은 예시로 바꿔 적었습니다.

```
운영: https://links.example.com/invite/{inviteKey}
개발: https://dev-links.example.com/invite/{inviteKey}
```

운영과 개발 도메인을 나눈 이유가 있습니다. 개발 빌드는 패키지명이 달라서 운영 앱과 한 기기에 같이 설치됩니다. 한 도메인을 두 앱이 모두 받겠다고 하면 같은 링크에 앱이 두 개 걸려서 테스트하다가 운영 앱이 열리는 일이 생깁니다. 개발 서버에서 만든 초대 키를 운영 서버에 물어볼 수도 없습니다. 도메인을 나누면 개발 빌드는 개발 도메인만, 운영 빌드는 운영 도메인만 받습니다.

## manifest: 이 주소는 내가 받겠다

앱 쪽 선언은 intent-filter 하나입니다.

```xml
<intent-filter android:autoVerify="true">
    <action android:name="android.intent.action.VIEW" />
    <category android:name="android.intent.category.DEFAULT" />
    <category android:name="android.intent.category.BROWSABLE" />
    <data
        android:scheme="https"
        android:host="${linkHost}"
        android:pathPrefix="/invite/" />
</intent-filter>
```

`autoVerify="true"`가 "설치할 때 이 도메인을 검증해 달라"는 뜻입니다. 이게 없으면 그냥 https 딥 링크로 취급되고 위에서 말한 대로 Android 12 이상에서는 브라우저로 열립니다.

host는 빌드 타입별로 다르게 넣었습니다. `build.gradle`의 `manifestPlaceholders`에 운영 빌드는 운영 도메인, 개발 빌드는 개발 도메인을 넣어 두면, 빌드할 때 manifest의 `${linkHost}`가 알맞은 값으로 바뀝니다. 빌드 후 merged manifest를 열어서 실제로 어떤 host가 들어갔는지 꼭 확인했습니다. 여기서 틀리면 앱 코드는 멀쩡한데 링크만 안 열리는 상황이 됩니다.

## 서버: assetlinks.json

검증은 서버 파일 하나로 이뤄집니다. 도메인의 `/.well-known/assetlinks.json`에 이 도메인을 받을 앱의 패키지명과 서명 인증서 지문을 적어 둡니다.

```json
[{
  "relation": ["delegate_permission/common.handle_all_urls"],
  "target": {
    "namespace": "android_app",
    "package_name": "com.example.app",
    "sha256_cert_fingerprints": [
      "AA:BB:...:업로드 키",
      "CC:DD:...:Play 앱 서명 키"
    ]
  }
}]
```

![앱 설치 시점의 도메인 검증 흐름](/uploads/1792990000000-applink-verification.svg)

여기서 실수하기 쉬운 부분이 세 가지 있었습니다.

**지문이 두 개 필요할 수 있습니다.** Play 앱 서명을 쓰면 개발자가 올리는 업로드 키와 사용자 기기에 실제로 설치되는 앱의 서명 키가 다릅니다. 스토어에서 받은 앱은 Play 서명 키로 서명돼 있으니 그 지문이 없으면 검증에 실패합니다. 반대로 내부 테스트용으로 직접 빌드한 APK는 업로드 키로 서명됩니다. 그래서 두 지문을 모두 넣었습니다. Play 서명 키 지문은 Play Console의 앱 무결성 메뉴에서 확인할 수 있습니다.

**개발 도메인에는 개발 앱을 적어야 합니다.** 처음 확인했을 때 개발 도메인의 파일에는 운영 패키지명만 들어 있었습니다. 개발 빌드는 패키지명이 다르니 이 상태로는 개발 앱이 절대 검증되지 않습니다.

**검증은 링크를 누를 때가 아니라 설치할 때 일어납니다.** 앱을 설치하거나 업데이트하는 시점에 OS가 이 파일을 가져갑니다. 그래서 배포 순서가 중요합니다. 서버 파일이 올라가기 전에 앱 업데이트가 먼저 나가면, 그 사이에 업데이트한 사용자 기기에서는 검증이 실패한 상태로 남습니다. OS가 나중에 다시 시도하긴 하지만 언제 할지는 보장되지 않습니다. 일정은 도메인 연결과 서버 파일 배포를 먼저 하고 앱은 그다음에 내보내는 순서로 잡았습니다.

## 앱: 주소에서 키를 꺼내 처리하기

링크를 눌러서 앱이 열리면 진입 Activity가 주소를 받습니다. 여기서 하는 일은 단순합니다. 구조만 의사코드로 적으면 이렇습니다.

```
onLinkOpened(uri):
    if uri가 https가 아니거나 host가 현재 환경의 링크 도메인이 아니면: 무시
    segments = uri의 경로 조각들
    if segments가 ["invite", key] 형태가 아니면: 무시
    서버에 key 확인 요청
        성공 → 초대 수락 화면 표시
        실패 → 서버가 준 안내 문구 표시 (만료, 이미 참여 등)
```

확인한 부분이 몇 가지 있습니다.

- **host를 다시 검사합니다.** intent-filter가 이미 걸러 주지만 진입 Activity는 다른 경로로도 열리기 때문에 코드에서도 현재 환경의 도메인인지 확인합니다.
- **경로 조각 개수까지 맞춥니다.** `/invite/` 뒤에 키가 하나만 있을 때만 처리하고 키가 비어 있거나 뒤에 경로가 더 붙어 있으면 무시합니다.
- **앱이 이미 켜져 있을 때도 처리합니다.** 앱이 꺼져 있다가 링크로 켜지면 첫 화면이 준비된 뒤에 초대 화면을 띄우면 됩니다. 이미 앱이 떠 있는 상태라면 진입 Activity를 거쳐 기존 화면으로 돌아오기 때문에, 그때는 바로 띄워 줘야 합니다. 두 상태를 모두 직접 눌러 보고 확인했습니다.
- **언어는 받는 사람 기준입니다.** 초대 정보를 서버에 물어볼 때 받는 사람의 앱 언어를 함께 보냅니다. 링크 주소에 언어를 넣으면 보낸 사람의 언어로 고정되기 때문입니다.

링크를 만드는 쪽은 더 간단해졌습니다. 예전에는 SDK에 링크 생성을 요청하고 결과를 콜백으로 기다렸습니다. 지금은 서버에서 초대 키를 받으면 주소 문자열 끝에 붙이기만 하면 됩니다. 실패할 수 있는 단계가 하나 줄었습니다.

## 웹 페이지의 '앱으로 열기' 버튼

앱이 없는 사람이 링크를 누르면 같은 주소의 웹 페이지가 열립니다. 메신저의 인앱 브라우저처럼 앱 링크를 앱으로 넘겨주지 않는 환경에서도 이 페이지가 보입니다. 그래서 페이지에 '앱으로 열기' 버튼을 두는데, 이 버튼의 주소를 정할 때 한 번 헷갈렸습니다.

![초대 링크 하나로 이어지는 전체 흐름](/uploads/1792990000000-applink-invite-flow.svg)

처음에 생각하기 쉬운 건 버튼에 같은 https 주소를 다시 거는 것입니다. 그런데 Chrome은 지금 보고 있는 페이지와 같은 도메인으로 이동하는 링크는 앱으로 넘기지 않고 페이지 안에서 이동시킵니다. 버튼을 눌러도 같은 페이지가 다시 열릴 뿐입니다.

Android에서는 이럴 때 Intent URI를 씁니다.

```
intent://links.example.com/invite/{inviteKey}#Intent;scheme=https;package=com.example.app;end
```

`scheme=https`와 host, 경로를 그대로 두고 `package`로 열 앱을 지정합니다. 이 주소를 누르면 Chrome이 "이 패키지의 앱에 https 링크를 넘겨라"라고 OS에 요청합니다. 앱이 설치돼 있으면 공유 링크를 눌렀을 때와 똑같은 처리로 들어가고 없으면 Play 스토어로 보냅니다. 스토어 대신 다른 곳으로 보내고 싶으면 `;end` 앞에 `S.browser_fallback_url=` 값을 URL 인코딩해서 붙이면 됩니다. 패키지를 직접 지정하기 때문에 도메인 검증이 아직 끝나지 않은 기기에서도 앱이 열립니다.

여기서 한 번 엇갈린 적이 있습니다. 처음 정리된 표에는 Android 쪽이 `scheme=myapp` 같은 커스텀 스킴으로 적혀 있었습니다. iOS는 같은 도메인에서 Universal Link를 눌러도 앱이 열리지 않아서 커스텀 스킴을 쓰는 경우가 많은데, 그 방식을 Android에도 그대로 옮긴 것이었습니다. 하지만 앱은 https 주소만 받도록 만들었으니, 커스텀 스킴으로 열면 앱은 켜져도 초대는 처리되지 않습니다. Android는 `scheme=https`로 두면 공유 링크와 '앱으로 열기'가 같은 처리 하나로 모입니다. 커스텀 스킴 처리를 따로 만들 이유가 없습니다.

## 검증은 adb로

서버 준비가 끝난 뒤에는 기기에서 검증 상태부터 확인합니다.

```bash
adb shell pm get-app-links com.example.app
```

출력에서 도메인 옆에 `verified`가 보이면 성공입니다. `1024`나 `legacy_failure` 같은 값이 보이면 서버 파일이나 지문을 다시 봐야 합니다. 서버 파일을 고친 뒤에는 다시 검증을 요청할 수 있습니다.

```bash
adb shell pm verify-app-links --re-verify com.example.app
```

링크 처리 자체는 메신저를 거치지 않고 바로 확인할 수 있습니다.

```bash
adb shell am start -a android.intent.action.VIEW \
  -c android.intent.category.BROWSABLE \
  -d "https://links.example.com/invite/test-key"
```

그다음 실제 메신저로 링크를 보내서 앱이 꺼진 상태와 켜진 상태에서 각각 눌러 보고 앱을 지운 기기에서는 웹 페이지와 '앱으로 열기' 버튼이 스토어로 이어지는지 확인했습니다.

## Branch를 걷어내면서 포기한 것

포기한 기능은 deferred deep link 하나입니다. Branch는 앱이 없는 사람이 링크를 누르면 스토어로 보내고 설치 후 처음 앱을 열 때 원래 누른 초대 키를 기억해서 넘겨 줬습니다. 앱 링크에는 이 기능이 없습니다. 지금은 앱을 설치한 뒤 링크를 한 번 더 눌러야 초대 화면이 뜹니다.

Play Install Referrer로 비슷하게 만들 수는 있지만 우선은 다시 누르게 하는 쪽으로 정했습니다. 초대는 보통 아는 사람끼리 주고받는 링크라서 설치 후 한 번 더 누르는 정도는 감수할 만하다고 봤습니다.

예전 Branch 초대 링크를 받던 코드도 함께 지웠습니다. 이미 보낸 옛 링크는 더 이상 동작하지 않습니다.

## 정리

해 보니 앱 코드는 생각보다 적었습니다. intent-filter 하나, 주소에서 키를 꺼내는 함수 하나, 링크를 만드는 한 줄이 전부였습니다. 시간이 걸린 건 앱 바깥이었습니다. 운영과 개발 도메인을 나누는 것, 서버 파일에 패키지명과 지문 두 개를 정확히 넣는 것, 서버를 앱보다 먼저 배포하는 순서, 그리고 웹 페이지의 '앱으로 열기' 버튼이 커스텀 스킴이 아니라 https Intent URI여야 한다는 것까지. 앱 링크는 앱, 서버, 웹이 같은 주소 하나를 두고 약속을 맞추는 작업에 가깝습니다.

다음으로는 친구 초대와 아이템 공유 링크도 같은 도메인 아래 경로만 바꿔서 옮길 예정입니다. 구조를 한 번 만들어 뒀으니 intent-filter에 경로를 추가하고 처리 함수만 붙이면 됩니다.
